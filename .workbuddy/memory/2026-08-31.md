# 2026-08-31

## MacDesktopNotify 横向竞品调查 + 优化方案 + Linus Review

产出：`docs/reviews/2026-08-31-competitive-analysis-and-review.md`（仓库未改源码，仅新增文档）

### 关键结论

- **定位**：产品横跨两个阵营。「刘海 UI 壳层」（Boring Notch / NotchNook / Alcove / MacNotch / Atoll / Droppy / Seam）UI 精致但**无外部推送入口**；「脚本通知通道」（alerter / terminal-notifier / ntfy / osascript）可编程但渲染交给系统通知中心。「刘海沉浸 UI + 可编程推送」是真实空白象限。已核实 Boring Notch 文档里的 Notifications 章节是内部 NotificationCenter 事件，不是用户推送入口。MacNotch 已在往该象限靠（自带通知与行内回复），窗口期有限。
- **护城河判断**：不是 UI（追不上 Boring Notch），而是 alerter 那套通知语义——消息不丢（持久化）、操作有回执、group 去重。

### 已复现的 P0 缺陷（重要）

`NotificationManager` 存在隐式不变量「只要 current 是非 critical 消息就必须有 dwell 定时器在跑」，但无代码负责维护，依赖 5 个调用点各自记得 arm。

触发路径：消息进入 → 指针悬停（dwell 暂停）→ 点击 ×（`dismissPanel` L226 调 `scheduleDwell`，被 L346 的 `!isHovering` 守卫静默 return）→ current 永久滞留 → `push()` 在 `current != nil` 且非 critical 时完全不动作（L89-98），后续所有普通消息静默入队丢弃。应用表现为「死了」。

- 复现方法：临时 XCTest（`islandClicked()` → `setHovering(true)` → `dismissPanel()` → sleep 2s → XCTAssertNil(current)），两条断言均失败。已删除临时文件，测试代码收录在报告 §3.2①。
- 现有 42 测试全绿却漏掉此路径——已有回归测试只覆盖 `setHovering` 路径，未覆盖 `dismissPanel` 这条退出路径。
- **推荐修法**：不要加 `isHovering = false` 打补丁，应把 `current` 编入 `IslandDisplayState` 枚举 payload（`.transient(item:remaining:)` / `.blocking(item:)`），使非法状态在类型层面不可表达。

### 其他发现

- 性能：`NotchPresenter` 每个 mouseMoved 分配一个 `Task`；开启「全屏隐藏」后每次鼠标移动执行 `CGWindowListCopyWindowInfo`（默认关闭所以未暴露）。
- `MarkdownNotificationView.blocks` 是计算属性，`LazyVStack` 滚动时每次重解析 Markdown，需缓存。
- 单显示器：`NotchPresenter` 只建一个 DynamicNotch，但 `DynamicNotchKit` 的 `expand(on: NSScreen)` 支持多屏。
- README 写 timeout 默认 5，`URLNotificationParser.defaultTimeout = 6` 是永不可达的死值（实际走 `AppSettings.messageDwellSeconds`）。
- `Package.swift` 依赖 DynamicNotchKit 用 `branch: "main"`，未锁定。
- CLI v1 设计（`docs/superpowers/specs/2026-07-15-notchnotify-cli-design.md`）已批准但未实现，设计质量高，可直接实施。

### P0 修复已落地（同日）

改动只在两个文件：`Sources/MacDesktopNotify/NotificationManager.swift` + `Tests/MacDesktopNotifyTests/IslandStateTests.swift`（+4 测试）。其他 4 个已修改文件是开工前就有的，未触碰。

**方案（与报告 §3.2① 建议一致，但做了取舍）**：

1. 新增 `struct Presentation { let item: NotchNotification; var remaining: Duration? }`——消息与 dwell 预算绑成一个值，`nil` 表示 blocking。`current` 改为从 `presentation` 派生的计算属性。
2. 新增 `reconcileDwell()` 作为 dwell 的**唯一决策点**，所有状态迁移末尾统一调用。核心守卫：
   ```swift
   private var dwellHeldOpen: Bool {
       (isHovering && displayState.isExpanded) || displaySuppressed || displayState == .manualExpanded
   }
   ```
   `isHovering && displayState.isExpanded` 是关键——悬停只在确实还有面板时才 Hold 倒计时，面板收起后残留的 isHovering 不再阻塞。这样即便 SwiftUI 漏发 `onHover(false)` 也不会再滞留消息。
3. `push()` 在 `presentation != nil` 分支加 `reconcileDwell()` 兜底，防止将来再次退化成应用假死。
4. `maxQueue` 拆名为 `maxHistoryCount` / `maxPendingCount`。

**未采用 Linus 原建议（把 current 编进 IslandDisplayState 枚举 payload）的理由**（已写入报告 §7.3）：
- `current` 是 SwiftUI 依赖的 `@Observable` 存储属性，改成枚举 payload 会让所有读 `displayState` 的视图在消息轮转时全部失效重绘。
- `displayState` 描述「窗口在做什么」，与「哪条消息在场」正交，合成一个枚举反而放大状态空间。
- `Presentation.remaining: Duration?` 已使「有消息但无清除者」不可表达，目标一致。

**验证**：`swift test --disable-sandbox` → 46 tests / 0 failures，无警告；`swift build -c release --disable-sandbox` → Build complete。

**测试踩坑**：写 `testLaterPushIsNotStarvedAfterPanelDismissal` 时最初断言 `current == nil` 失败——因为指针始终悬停在展开面板上时新消息本就该保持不收起，是断言写错不是代码问题。改为先断言 `current?.title == "second"`（未被饿死），再 `setHovering(false)` 后断言过期。

## P1 阶段：通知语义四项全部落地

用户「开干吧」后继续实施报告 §4.2。测试 46 → **96**，release 构建干净、零警告。

### 1. 持久化 — `NotificationHistoryStore.swift`（新）
`HistorySnapshot` 带 schemaVersion；解码失败整体返回 nil、**永不抛错**（历史读不出不能阻止启动）；`.atomic` 写入；**防抖 500ms**（`persistDebounce`）；`historyStore` 为 nil 时不落盘（测试不碰真实磁盘）。历史上限 10 → 50，新增 `persistHistory` 开关。

### 2. group 去重
同 group 新消息顶掉旧的历史/队列/屏上三者，并 `readIDs.subtract` 被顶替者（否则已读状态会泄漏）。`groupingKey` trim 且拒绝空白串，长度上限 64。新增 `notch-notify://clear?group=xxx`。

### 3. 动作回执 — `NotificationAckStore.swift`（新）
`notch-notify://ack?token=&label=` 是回环，记为回执、不交 `NSWorkspace`。token 校验 `alphanumerics.union("-_")`，拒绝 `..%2F` 与 `a%2Fb`（测试断言 `/etc/passwd.json` 未创建）。`push()` 改为返回 `Bool`（是否上屏），AppDelegate 据此决定是否发声。

### 4. 勿扰感知 — `PresenceMonitor.swift`（新）
三档 `QuietMode`：off / historyOnly / criticalOnly，默认 off。
- **`AwaySource` 用集合不用布尔**：屏保→锁屏→睡眠可叠加，单 Bool 会被第一个「结束」事件清掉别人仍持有的状态。
- 除监听 `com.apple.screenIsLocked/Unlocked` 等公开分布式通知外，启动/唤醒时用 `CGSessionCopyCurrentDictionary()` 的 `CGSSessionScreenIsLocked` **主动查询**——机器可唤醒到仍锁着的会话，不会有通知来纠正。
- **不接管 `displaySuppressed`**（归全屏检测所有，NotchPresenter 调用），两轴独立。

**主动偏离报告 §3.2⑤**：未实现 DND/Focus 感知。macOS 无公开 API，唯一途径是读未文档化且跨版本搬迁过的 preference key。会静默失效的勿扰比没有更糟。接缝留在 `PresenceMonitor.setActive(_:for:)`。

**已知限制**：离开瞬间屏上已有的消息不主动收起（瞬态消息自然退场，critical 按设计留守）。干净做法需单独设计，见报告 §8.7。

### 设计决策记录
- `settleAfterWithdrawal` 只在「group 折叠把屏上消息退下来 + 静默替代者不补位」时 repair，**只在 `displayState.isExpanded` 时动**——否则会在锁屏上点亮胶囊，与静默意图相反。
- Swift 6 下 `deinit` 不能调用 `@MainActor` 方法，`PresenceMonitor` 去掉 deinit，生命周期只由 `start()/stop()` 表达。

## P2 阶段：四项全部落地

测试 96 → **111**，release 构建零警告。

### 5. Markdown 缓存 — `MarkdownCache.swift`（新）
`blocks`/`previewText` 是 SwiftUI 计算属性，每次 body 求值重解析。双层 `NSCache`（countLimit 200 / totalCostLimit 4MB），键即正文字符串（相同内容天然共享）。暴露 `blockHits/blockMisses` 作可测接缝——断言第二次渲染命中，而非「能编译」。

### 6. 鼠标监控性能（两处独立问题）
- **去重在 actor 跳转之后**：原实现先建 Task 再判 1px 阈值，等于每个 mouse-moved 分配一次 Task。改为锁内同步判阈值，用 `OSAllocatedUnfairLock`（全局监视器不保证在主线程）。
- **`CGWindowListCopyWindowInfo` 在热路径**：原 200ms 节流 = 鼠标持续移动时每秒 5 次。改为按 `(前台 pid, screenID)` 缓存 + 应用激活/空间切换/屏幕变化时失效 + 指针移动时兜底 2s + **无消息时完全跳过**。常规场景零次，有内容时约 0.5 次/秒。

### 7. 多显示器 — `PerScreenInstances.swift`（新）
`DynamicNotchKit` 约定「一个实例一个 notch」，故每屏一个实例。
- 泛型容器 `PerScreenInstances<Instance>` 抽出来单独测（真实 DynamicNotch 需窗口服务，测试建不出来）。8 项测试，含实例身份保持：改分辨率不重建，拔插才重建。
- 屏幕标识用 `CGDirectDisplayID` 而非 `NSScreen` 实例——后者每次屏幕参数变化都重建，跨时间不能做键。
- 一个逻辑刘海跟随指针：expand/compact 作用于指针所在屏，其余 hide；hide 作用于全部；跨屏时重放状态。

### 8. 依赖锁定
`branch: "main"` → `from: "1.1.0"`。**用户确认的取舍**：main 比 1.1.0 多一个提交 46c2af2「Capsule 形状修复」（仅影响 pill 样式，刘海样式不受影响），锁定后暂不含。上游发 1.1.1 后可自动获得。

### Swift 6 坑（本次遇到两次）
`deinit` 不能访问 `@MainActor` 隔离的状态（`PresenceMonitor`、`NotchPresenter` 各踩一次）。解决办法：去掉 deinit，生命周期只由 `start()/stop()` 表达，并注释说明原因——两个对象都由 AppDelegate 持有、贯穿整个进程。
另：在锁内非隔离执行的常量/方法需标 `nonisolated`（`pointerEpsilon`、`isMovementWorthReporting`）。

### 未实测（诚实记录）
多显示器窗口行为、全屏探测频次改善、Markdown 缓存渲染收益——本环境无 GUI、无外接显示器。已写入报告 §9.6。
